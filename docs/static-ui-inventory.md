# アプリ一覧からの静的UI一括点検

## 計画と優先度

一覧に載っているアプリを、指定したときにまとめて読取専用で点検する。既存の定期収集は主にHTTPと版の観測、一覧の対応検査はIDの整合、既存のブラウザ試験は合成画面と個別アプリの操作を扱う。本点検は各入口のHTMLにある版履歴リンク・テーマアイコン・一覧への導線の静的な手掛かりを集め、認証・接続・リダイレクト・取得できない内容を区別する。

事前評価は89点（利用価値32/35、共通性23/25、実現性17/20、検証・復旧17/20）。一覧変更後の横断的な点検を一回で始められる便益を評価した。速さや作業時間の短縮量は測定していない。実装・実行・検査が終わるまでは完了数に加えない。

## 操作と制約

```sh
python3 tools/static_ui_inventory.py --ca-file "$HOME/anti/.local/share/hubterm/hubterm-ca.pem"
```

公開CAの場所は実環境に合わせる。通常の信頼ストアで検証できるなら `--ca-file` は省略できる。対象を絞るときは `--id equalification --id video-player-2d` のように指定する。標準出力はJSONで、`summary` は取得区分と静的な手掛かりの件数、`results` は各観測IDの詳細を表す。`ok: true` は点検処理を実行できたことを示し、全アプリの稼働や適合を保証しない。結果をファイルに保存するときは、利用環境に合うアクセス制限を付ける。

点検結果には、同じIDが後から別の入口を指した場合に区別できるよう、一覧に記載されたURLのSHA-256を含める。URLのパス・クエリ原文は記録しないが、ハッシュは秘密化の保証ではない。結果の前回比較は [比較手順](static-ui-inventory-comparison.md) を参照する。

- 起動は手動。許可済みの一覧のサービスURLだけを使い、資料リンクは稼働アプリと数えない。未登録のスキーム・ホスト・ポートの組合せや資格情報付きURLは取得しない。新しい入口は許可先を確認してから登録する。
- 認証情報・Cookie・プロキシを使わず、GETだけを送る。自動リダイレクト、JavaScript、画像、CSS、アプリAPIは実行・取得しない。HTTPSの証明書は通常通り検証し、必要に応じて既存の公開CAを指定する。
- 各応答には容量上限を設ける。HTML本文、画像、URLのパス・クエリ、例外本文を出力・保存しない。結果に残すのは一覧の観測ID、時刻、HTTP状態区分、静的な手掛かりと版表記だけ。
- 認証・権限制限（HTTP 401/403）・接続不能・証明書・リダイレクト等は機能の有無と分ける。401/403だけで原因がログイン必須だとは断定しない。HTML中に見つからない場合は「未観測」とし、機能がないと断定しない。JavaScriptで追加されるUI、画面上の位置・固定、実際のテーマ切替、復元の成功は判定できない。
- GETでもサーバー側で副作用が起こらない保証はない。信頼できる一覧だけを対象とし、不要な高頻度実行や並列アクセスを行わない。

## 受入と復旧

合成サーバーで正常・認証・転送・TLS失敗・容量超過・拒否ホストを確認し、転送先や書込みAPIへ到達しないことを検査する。221の既存環境で同じテストを動かし、認可済みアプリの一回の点検結果を別の観測と照合する。実画面やユーザーデータが未確認であることを記録する。戻す場合はこのツールとテストを取り除き、アプリや収集データは変更しない。
